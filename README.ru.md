# Tickr

[English](README.md) · Русский

Дашборд котировок в реальном времени: свечи, стакан и лента сделок поверх публичного WebSocket Binance.
Пет-проект под задачи уровня Т‑Инвестиций: высокочастотные данные, минимум лишних ререндеров.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173 (хост WS меняется через VITE_WS_HOST)
npm test           # unit + компонентные тесты
npm run build      # typecheck + продакшен-сборка
```

## Архитектурные решения

| Проблема | Решение |
| --- | --- |
| Сделки приходят десятки раз в секунду | События копятся и применяются одним батчем на `requestAnimationFrame` (`marketFeed.ts`) |
| Обрывы соединения | `createReconnectingSocket` с экспоненциальной задержкой, сброс при успешном `open` |
| Лишние ререндеры | Мини-стор на `useSyncExternalStore` с селекторами: компонент обновляется, только если изменился его срез |
| График на 120 свечей, обновление до 10 раз/с | Canvas рисуется императивно по подписке на стор, минуя React |
| Мусорные сообщения | `parseMessage` возвращает `null`, фид не падает |
| Тестируемость | Чистый редьюсер `reduceEvent`, парсер и математика графика отделены от UI |

## Производительность

Замеры на продакшен-сборке (`npm run build && npm run preview`), BTCUSDT, 30 секунд после прогрева, в одной сессии Chrome. Коммиты React считаются по компонентам счётчиком в `useEffect` (`src/shared/perf.ts`), поэтому двойной рендер StrictMode не искажает цифры.

`?naive=1` отключает две основные оптимизации и даёт базовую линию: события применяются по одному, а не одним батчем на кадр, и каждый компонент подписан на весь стейт, а не на селектор.

| Метрика (30 с) | Наивный режим | Оптимизированный |
| --- | --- | --- |
| Сообщений WebSocket | 3 834 | 3 925 |
| Коммитов React, всего | 19 170 | 1 007 |
| Коммитов на сообщение | 5,00 | 0,26 |
| Ticker | 3 834 | 137 |
| OrderBook | 3 834 | 292 |
| TradeList | 3 834 | 196 |
| CandleChart | 3 834 | 15 |
| Long tasks (>50 мс) | 0 | 0 |

Это примерно в 19 раз меньше коммитов React на тот же поток данных. Long tasks в обоих режимах нулевые: на этой машине разница проявляется в лишней работе, а не в видимых тормозах, на слабом устройстве её стоит искать там. Это один 30-секундный прогон на режим, а не статистический бенчмарк.

Как повторить: откройте preview, выполните в консоли `__perf.reset()`, подождите и выполните `__perf.snapshot()`. Для базовой линии добавьте к адресу `?naive=1`.
