# Tickr

[English](README.md) · Русский

Дашборд котировок в реальном времени: свечной график, стакан и лента сделок на публичных рыночных данных Binance. Создан, чтобы исследовать высокочастотный UI: тысячи обновлений в минуту при минимуме лишних ререндеров.

## Возможности

- Живой свечной график 1м со шкалами цены и времени, меткой текущей цены и перекрестием с легендой OHLC
- Индикаторы SMA 20, EMA 50 и Bollinger Bands поверх свечей, отдельная панель RSI 14 и значения для выбранной свечи
- Вычисление индикаторов в Web Worker с автоматическим fallback в основной поток
- Стакан с полосами глубины, спредом между лучшими ценами и скелетонами при загрузке
- Лента сделок с подсветкой новых строк
- Статистика за 24ч: изменение, максимум, минимум, объём
- BTC, ETH и SOL к USDT, переключение без перезагрузки страницы
- Автоматическое переподключение с видимым статусом соединения
- Адаптивная вёрстка (десктоп, планшет, телефон), управление с клавиатуры, поддержка `prefers-reduced-motion`

## Запуск

Нужен Node.js 20+.

```bash
npm install
npm run dev
```

Откройте http://localhost:5173.

### Настройка

Рыночные данные берутся с публичного зеркала Binance `data-stream.binance.vision`: оно доступно там, где `stream.binance.com` заблокирован. Адреса меняются переменными окружения:

```bash
VITE_WS_HOST=wss://stream.binance.com:9443 VITE_API_HOST=https://api.binance.com npm run dev
```

## Node.js-прокси

Необязательный прокси (`server/`) стоит между браузером и Binance. Он полностью заменяет биржевые адреса: отдаёт те же `/stream` (WebSocket) и `/api/v3/klines` (REST), поэтому фронтенду нужны только две переменные окружения.

```bash
npm run server        # прокси на :8787
npm run dev:proxy     # фронтенд, направленный на прокси
```

Что он делает:

- **Одно соединение с биржей на символ**, общее для всех клиентов. Открывается при первом подписчике и закрывается через 10 секунд после ухода последнего.
- **Снимок при подключении**: последнее сообщение каждого стрима кэшируется, поэтому новый клиент сразу получает стакан, статистику и свечу, а не ждёт следующего обновления.
- **Общий REST-кэш**: история свечей кэшируется на 5 секунд, параллельные запросы склеиваются в один запрос к бирже, а при недоступности биржи отдаётся устаревшее значение.
- **Защита от медленных клиентов**: если буфер отправки клиента больше 1 МБ, ему не шлют новые сообщения, и память не растёт.
- **Валидация**: принимаются только известные символы и каналы, не более 8 стримов на соединение и не более 1000 клиентов.
- **Здоровье**: ping/pong отсекает мёртвые сокеты, `GET /health` отдаёт счётчики хаба и кэша.

Настройка (переменные окружения): `PORT` (8787), `UPSTREAM_WS_HOST`, `UPSTREAM_API_HOST`, `KLINES_TTL_MS` (5000).

Наблюдение на живом запуске, интерфейс в браузере и ещё четыре клиента на BTCUSDT: 5 клиентов использовали 1 соединение с биржей (`upstreamsOpened: 1`), а 2 параллельных запроса свечей привели к 1 запросу к бирже (`misses: 1, coalesced: 1`). Dev-интерфейс запрашивает историю дважды из-за StrictMode. Без прокси было бы 5 соединений и 2 REST-запроса.

## E2E-тесты

Тесты Playwright запускают весь стек локально: подставной upstream Binance (`e2e/fakeUpstream.ts`), настоящий Node.js-прокси и настоящий фронтенд. Сеть не используется, поэтому тесты детерминированы и не требуют доступа к бирже.

```bash
npx playwright install chromium   # один раз
npm run e2e
```

Покрытые сценарии:

- цена, стакан, лента сделок и график появляются, на странице нет ошибок
- переключение BTC, ETH и SOL меняет данные и заголовок страницы
- обрыв соединения браузера с прокси: статус показывает переподключение, затем данные возвращаются
- обрыв соединения прокси с биржей: прокси сообщает `reconnecting`, интерфейс замирает без ошибок, поток восстанавливается, когда upstream вернулся
- две вкладки браузера делят одну комнату прокси
- индикаторы включаются, получают значения и отображают RSI без ошибок страницы
- при недоступном Web Worker индикаторы вычисляются в основном потоке

Подставной upstream отдаёт `/__control/block` и `/__control/unblock`, чтобы имитировать сбой биржи. В CI набор запускается в официальном образе Playwright, HTML-отчёт и трейсы сохраняются артефактами.

## Архитектурные решения

| Проблема | Решение |
| --- | --- |
| Сделки приходят десятки раз в секунду | События копятся и применяются одним батчем на `requestAnimationFrame` (`marketFeed.ts`) |
| Обрывы соединения | `createReconnectingSocket` с экспоненциальной задержкой, сброс при успешном `open` |
| Лишние ререндеры | Мини-стор на `useSyncExternalStore` с селекторами: компонент обновляется, только если изменился его срез |
| График на 120 свечей, обновление до 10 раз/с | Canvas рисуется императивно по подписке на стор, минуя React |
| Расчёт индикаторов при живом потоке | Web Worker; пока идёт расчёт, копится только последнее состояние, а при недоступности Worker используется fallback в основном потоке |
| Свечи в стриме приходят только за текущую минуту | История загружается по REST и склеивается с live-свечами, при конфликте приоритет у live |
| Мусорные сообщения | `parseMessage` возвращает `null`, фид не падает |
| Тестируемость | Чистый редьюсер `reduceEvent`, парсер, индикаторы и математика графика отделены от UI |

```
    marketFeed.ts         сокеты, батчинг, загрузка истории

  hub.ts                  upstream на символ, раздача клиентам, кэш снимков

  streams.ts              валидация запросов
  app.ts                  HTTP- и WebSocket-сервер
  index.ts                точка входа

  fakeUpstream.ts         подставной Binance для детерминированных тестов
  dashboard.spec.ts       сценарии Playwright
```

## Производительность

Замеры на продакшен-сборке (`npm run build && npm run preview`), BTCUSDT, все индикаторы включены, 30 секунд после 5-секундного прогрева, два последовательных прогона в одном headless Chromium. Коммиты React считаются по компонентам счётчиком в `useEffect` (`src/shared/perf.ts`), поэтому двойной рендер StrictMode не искажает цифры.

`?naive=1` отключает две основные оптимизации и даёт базовую линию: события применяются по одному, а не одним батчем на кадр, и каждый компонент подписан на весь стейт, а не на селектор.

| Метрика (30 с) | Наивный режим | Оптимизированный |
| --- | --- | --- |
| Сообщений WebSocket | 3 293 | 2 425 |
| Коммитов React, всего | 16 479 | 897 |
| Коммитов на сообщение | 5,00 | 0,37 |
| Ticker | 3 293 | 94 |
| OrderBook | 3 293 | 296 |
| TradeList | 3 293 | 136 |
| CandleChart | 3 307 | 30 |
| Spread | 3 293 | 341 |
| Расчётов индикаторов | 14 | 15 |
| Время расчётов индикаторов, мс | 2 | 2 |
| Long tasks (>50 мс) | 0 | 0 |

В этих прогонах оптимизированный режим дал примерно в 18 раз меньше суммарных коммитов React и в 13,5 раза меньше коммитов на сообщение. Потоки живые, поэтому число сообщений различается. Long tasks в обоих режимах нулевые: на этой машине разница проявляется в лишней работе, а не в видимых тормозах, на слабом устройстве её стоит искать там. Это один 30-секундный прогон на режим, а не статистический бенчмарк.

Как повторить: откройте preview, включите все индикаторы, подождите 5 секунд и выполните в консоли `__perf.reset()`. Через 30 секунд выполните `__perf.snapshot()`. Для базовой линии добавьте к адресу `?naive=1`. Снимок также содержит `indicatorRuns` и `indicatorMs` — количество и суммарное время расчётов индикаторов. Параметр `?noWorker=1` принудительно выполняет их в основном потоке.
